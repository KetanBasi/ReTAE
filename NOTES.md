# NOTES — decisions, known limits, fixable issues

Living document, not a changelog. Edit an entry in place when its status changes and delete it when
fixed (git history is the log). Tags: **[fixable]** we know how · **[by design]** intentional, revisit
only if a goal changes · **[unproven]** needs hardware or another machine, see `TODO.md`.

## Decisions
- **A2** The engine is 48 kHz only. Peers at other rates are dropped and counted (`wrong_rate`); backends must open devices at 48 kHz.
- **A3** RX trust: a stream naming a source IP trusts exactly that IP; wildcard streams accept only `RxPolicy.allowed` (or anyone with the expert `accept_any`). VBAN-TEXT follows the same rule. VBAN-SERVICE is open (discovery needs it) but replies are LAN-only and rate-limited.
- **A4** TX wakes on a 1 ms `park_timeout` tick, not `atomic-wait` (no timed wait, and the RT thread may not make a syscall).
- **A5** The drift resampler is our own cubic Hermite; rubato is a dev-dependency only (benchmarks and comparison).
- **A6** Contract additions to `audio-types` so far: `ClockDomain` + `EngineCommand::SetStripClock` (S2), `LanTxConfig.duplicate` (S3, `serde(default)`). S4 added none; its only `audio-engine` change is `InputPort`/`OutputPort::into_parts`/`from_parts`, so a net stream can own a ring half and hand it back to the pool.
- **A7** Control plane (S4): the UI, CLI and daemon talk through `app_core::ControlApi`. `LocalControl` implements it in-process; `RemoteControl` implements it over IPC (a `interprocess` local socket, abstract namespace on Linux and a named pipe on Windows, with u32-LE length-prefixed postcard frames, 1 MiB max). `PROTOCOL_VERSION` (types.rs) is bumped whenever a message changes shape; the handshake refuses a mismatch. The single-instance lock is "connect to the name, and refuse if something answers", then bind; there is no lock file, so a killed daemon leaves nothing stale.

## audio-engine (S1)
- **E1** [by design] A port ring is 32 768 f32: 8 ch × 4096 frames = 85 ms at 8 channels (341 ms at stereo). An 8-channel strip with a target above 85 ms (VerySlow = 96 ms, large Custom) cannot be buffered. Fix if needed: bigger rings (48 × 128 KB = 6 MB today) or clamp the target by channel count.
- **E2** [unproven] Worst-case 16×16 bench is 27–37 µs per block (41.6 µs with a drift adapter on every strip; budget 50 µs), measured on a shared 2.1 GHz VM in release.
- **E3** [by design] `assert_no_alloc` guards debug and test builds only.
- **E4** [by design] Rejected (invalid) commands are counted in `EngineStats`; the UI shows the count in the toolbar status, and a command the daemon refuses is shown in the status line and reverted (U3).

## drift (S2)
- **D1** [fixable] With chunky producers (one packet ≈ one block, e.g. the 128-frame default) the fill seen at block starts is a staircase the 1 s EMA cannot smooth: the smoothed fill swings up to half a packet (2.1 ms at 208 ppm). At Optimal (6 ms) that leaves ~0.3 ms of headroom. Measured with a clean wire (`SIM_PPM=… trace_one`, 2 min): ±50/±100 ppm stay without underrun or prediction but the pre-pull fill dips to 3.1–3.3 ms (2.67 ms is the underrun line); at an unrealistic 208 ppm the controller never settles (applied ratio swings 0 to −570 ppm, fill 4.5–6.7 ms). Cause: with packet = block the sampled fill only changes in 128-frame steps once per beat (1/ppm blocks), and each step kicks the integrator. Fix needs a phase tracker (interpolate the fill between detected steps, or arrival timestamps relative to pulls); a simple gain/EMA change only trades one effect for another. Not done: Fast and above have the headroom, and N1 now turns an Optimal dip into a short concealment instead of an underrun.
- **D2** [by design] Hermite is for ±1000 ppm drift only (THD+N −91.7 dB at 1 kHz, −49 dB at 5 kHz, −29 dB at 10 kHz). It is not a sample-rate converter; if one is ever needed use rubato behind `DriftResampler`.
- **D3** [by design] Offsets beyond ±1000 ppm saturate the controller; the adapter then relies on its underrun/overrun handling.
- **D4** The controller uses conditional-integration anti-windup (amended in S3 after the jitter sims showed windup). Undershoot after a high start stays < 1.6 ms in the regression test.

## net-vban (S3)
- **N1** [by design] Predictive concealment (`StreamRx::predict`): when the ring is below one engine block and no packet has arrived for 1.5 packet periods (2.5, 3.5, … for each further predicted packet), the expected packet is declared lost and concealed before the mixer can underrun. It needs the RX clock (`set_time_us`; without one it never fires), is capped at 4 packets in a row (a dead sender then gets a real underrun) and makes the thread poll every 1 ms while the ring is below block + packet (nearly always at Optimal). Trade-offs: a packet that is merely very late is concealed and then counted as lost *and* late; a stream that stops adds up to 4 `lost`. Result in the sims: Optimal at 1 % loss 40/40 clean (was 30/40), no spurious prediction on a perfect wire or with a ±208 ppm sender.
- **N2** [by design] Fast (12 ms) with jitter equal to the buffer is not guaranteed underrun-free (sim: 59/60 independent-delay and 58/60 in-order runs clean, the failures are start-up transients; before N1: 54/60 and 48/60). Exactly 0 underruns when the buffer can absorb the jitter (7 ms independent, 4 ms in-order). A start-up pre-roll was tried and rejected.
- **N3** [fixable] `AdaptiveTarget` (jitter.rs) is written and tested but not wired to the RX thread or telemetry (planned for S9).
- **N4** [fixable] RX/TX threads ask for real-time priority on Linux (rtkit) only when the host program registers `net_vban::hook::set_thread_start_hook`, which `routerd` does in `main` (it needs the `rt` feature). On Windows the same hook gives them MMCSS "Pro Audio" (S6, `rt::promote_current_thread` is MMCSS there and needs no feature; unproven until run on Windows); Android (`THREAD_PRIORITY_URGENT_AUDIO`, S8) is still to do. The rtkit path is **unproven**: the dev container has no rtkit, so it always reports "unavailable". It matters: in that container (a microVM) the 1 ms TX tick sometimes wakes 3–30 ms late, which is more than the 12 ms Fast buffer holds (one underrun, then a backlog burst that overruns).
- **N5** [fixable] Sockets are not rebound after an interface change (Wi-Fi roaming, NIC unplug); errors are counted (`socket_errors`) and the thread backs off 5 ms. Fix: rebind after N consecutive errors.
- **N6** [fixable] The beacon goes to `255.255.255.255:6980` only, which leaves through the default interface. Multi-homed hosts need per-interface directed broadcasts (`Service::set_targets`); `app-core` should enumerate interfaces.
- **N7** [by design] VBAN-TEXT handles only set-commands for `Strip[i]`/`Bus[i]` `Gain` (clamped −60…+12 dB) and `Mute`; queries and every other VoiceMeeter parameter are ignored and counted. Wider coverage is S9.
- **N8** [by design] Opus: mono/stereo, `RESTRICTED_LOWDELAY` (PLC only, no FEC); the header frame count is informational. Audio is IPv4 unicast only.
- **N9** [unproven] The PING0 layout, VBAN-TEXT header and service type/function bytes come from the public protocol description, not a capture. Windows qWAVE and the 1 ms timer (`timeBeginPeriod`, net-vban `timer.rs`) are compile-checked only.
- **N10** Live mDNS test is `#[ignore]` (needs multicast); run `cargo test -p net-vban --lib -- --ignored mdns`.
- **N11** The mixer loopback test (`tests/loopback.rs`) requires 0 engine underruns/overruns only when the host was quiet (worst wake-up delay < 6 ms, measured in the test); on a noisy host it prints `NOTE: noisy host` and allows up to 20 underruns/overruns and up to 20 lost/late packets per stream (a delayed packet is concealed by N1). The mixer-less link tests keep a 40 ms cushion in the ring (Slow preset) so a late packet is never mistaken for a lost one, and stop the receiver before taking the cushion. On a real host it should print no NOTE; if it does, that is a finding (see N4).
- **N12** Sockets ask for 256 KB kernel buffers (PLAN §4.3), best effort: Linux caps the request at `net.core.rmem_max`/`wmem_max`. `SO_REUSEADDR` is deliberately not set (on Linux it would let two sockets share a UDP port and split unicast between them).

## platform-io, app-core, routerd, router-cli (S4)
- **C1** [unproven] The mock backend (`MockBackend`: fake devices `mock-in-1/2`, `mock-out-1/2`, `app:1001/1002`, paced by their own threads, with injectable signals, drift and dropouts) is what tests use, and `TimerMaster` stands in for the master device (see P2). The Linux backends exist (section S5 below) but have only met a headless PipeWire with null sinks, never a sound card. The Windows backend (section S6 below) has **never run at all**: it is compile-checked for `x86_64-pc-windows-gnu` only. Android is S8. `--backend` accepts `mock`, `pipewire`, `alsa`, `wasapi`, `auto`; the Linux ones need their cargo feature, `wasapi` works only in a Windows build.
- **C2** [by design] `router-cli probe` measures what a probe can honestly measure today. The **round trip** is `Service::ping` to a router or VoiceMeeter (VBAN-SERVICE, the peer answers at most one ping per 250 ms, so pings are 300 ms apart). The **click loop** feeds single-frame clicks through a borrowed free strip and bus (strip → FIFO at `device_target_ms` → mixer → bus → output ring) and times them. It covers the mixer path **only**, not the device or OS buffers and not the network (`ClickLoopReport.scope` says so and the CLI prints it). `expected_ms` is the configured FIFO target and the gate is ±1 block (2.67 ms). On a quiet dev host the median measured 7.85–8.75 ms against 8 ms (min ~5.4–6.6, max ~8.6–10.1). On a noisy one `host_noise_ms` (the worst 1 ms-sleep overshoot) reads 6.7–23 ms and the tests then widen their tolerance (`NOTE: noisy host`). The probe holds the control lock only while it sets up and tears down its rig; other commands wait for that, meters stay live.
- **C3** [fixable] Bus outputs have no drift resampler *in the engine*: only the master clocks the mixer. The real backends therefore resample on the device side: the PipeWire playback callback and the ALSA output callback each run a `ClockDomainAdapter` on the bus ring (`ring_io::PlaybackState`, P3). The mock outputs still drain at the nominal rate. WASAPI does the same (W1).
- **C4** [fixable] `Command::BusRecord` reaches the engine, which fills the recorder ring, but nothing drains it: the recorder is S9. Do not offer recording in a UI before then.
- **C5** [fixable] `routerd` has no signal handling: Ctrl-C ends the process without the orderly `Daemon` drop (sockets close with the process, so nothing is left behind, but devices and streams are not closed in order). Add a handler (`ctrlc`/SIGTERM) when a real backend needs a graceful stop.
- **C6** [by design] `RxSocket::set_policy` takes effect between receives (≤ 5 ms), so a packet sent the instant after `Command::RxPolicy` can still meet the old policy. Harmless for people; tests sleep 30 ms.
- **C7** [by design] `LocalControl` serialises commands behind one mutex and waits up to 500 ms for command-queue space (queue 1024, ≤ 256 applied per block). A profile load closes every link first, pushes parameters, then opens endpoints, so a failing device shows as `LinkState::Failed` instead of aborting the load. `RxPolicy.allowed` follows mDNS-discovered machines when `trust_discovered` is on (refreshed every 500 ms).

## Linux backends: PipeWire, ALSA, real-time priority (S5)
- **P1** [by design] PipeWire needs 0.3.49 or newer at run time (`Buffer::requested`; Ubuntu 22.04 has 0.3.48, 24.04 is fine). The `pipewire` crate's objects are `!Send`, so one thread, `pipewire-loop`, owns every PipeWire object; the control thread talks to it over a `pw::channel` and reads a shared `GraphState` snapshot filled from registry events. Stream callbacks run on PipeWire's data thread with `RT_PROCESS` and take the port with `try_lock`, never `lock`; `close` destroys the stream first and only then takes the port back.
- **P2** [by design] `TimerMaster` is still the mixer clock on Linux. No device clocks the mixer, so *every* device, including the first output, goes through a FIFO and the drift resampler (law 2 is satisfied, but PLAN §5.1's "master device" optimisation is not done). The floor is therefore the output target (8 ms by default, `output_target_ms`, which must exceed one 2.7 ms block because the mixer hands blocks over in bursts) plus the device quantum. Revisit with real latency numbers (TODO).
- **P3** [by design] `ring_io` (shared by both backends) holds the device-callback state. The output side runs a `ClockDomainAdapter` on the bus ring, so a card whose clock differs from the mixer's is steered by the PI controller (clamped ±1000 ppm, ≤ 10 ppm per block) instead of slowly over- or underrunning. The dev container's timer jitter shows up as large `clock_ppm` on the output (hundreds of ppm in a 1 s test); that is the controller working, not a fault.
- **P4** [by design] Virtual nodes are streams that exist only while open: `retae-virtual-in-N` (`Audio/Sink`) and `retae-virtual-mic-N` (`Audio/Source`, `node.virtual`), N = 0..3, shown to people as "ReTAE Virtual Input/Mic N+1". The mic is **not** `Audio/Source/Virtual` as PLAN said: on PipeWire 1.0.5 that class never gets capture ports (even `pw-loopback` shows it), WirePlumber logs "Failed to create links because of wrong ports" and nothing can record from it. Nodes whose name starts with `retae-` are never offered as devices. A session manager (WirePlumber) must be running for other programs to be linked to them.
- **P5** [by design] Per-app capture (`ProcessLoopback`) lists a program by pid and links all of that pid's `Stream/Output/Audio` output ports to our capture node, re-evaluated on every registry change so a program that starts later is picked up. The pid comes from the node, else its client's `application.process.id`, else the server-stamped `pipewire.sec.pid` (`pw-cat` sets none; inside a Flatpak that pid is namespaced). Child processes are not followed (so `IncludeTree` behaves like `Include`), `ExcludeTree` is Windows-only and answers `NotSupported`. `AppInfo.playing` is true while one of its streams is in the `running` state.
- **P6** [by design] ALSA (`cpal`) has hardware inputs and outputs only: no virtual devices, no device loopback, no per-app capture (`Capabilities` says so). It asks for 48 kHz with a 128-frame buffer, falls back to the device's default buffer, and to 16-bit samples when `f32` is refused. Listing devices opens each one briefly, so refresh on request only. Ids are cpal strings like `alsa:hw:CARD=...`. Unproven on real hardware: the container has no sound card.
- **P7** [unproven] Real-time priority: `rt::promote_current_thread` (rtkit through `audio_thread_priority`, D-Bus) is called on the mixer thread, whose outcome is `MasterStats.rt` and is printed by `routerd`, and on the net threads through the hook (N4). Never promoted in the container (no rtkit); a refusal is not an error. The PipeWire data thread is promoted by PipeWire itself.
- **P8** [by design] Streams ask for 48 kHz interleaved `f32`; PipeWire's stream converter bridges a graph at another rate (A2). 1–8 channels; 5 and 7 channels leave the layout to the server.
- **P9** [by design] Live tests (`platform-io/tests/pipewire_live.rs`, `routerd/tests/pipewire_e2e.rs`) need a PipeWire server and WirePlumber, print `SKIP:` and pass without one, and clean up after themselves (fake cards are owned by a `pw-cli` child). They use `pw-cat` through WAV files because PipeWire 1.0's `pw-cat` goes through libsndfile. They run only with `--features pipewire`.
- **P10** [fixable, unproven] Hot-unplugging a device while its stream is open is neither handled nor tested: nothing watches the stream's state after it opened, so the control plane would keep showing the link as `Running`. The ALSA error callback only counts an xrun. (WASAPI is better off: the worker thread stops and `AudioStream::detail()` says why, W6; the control plane still shows `Running`.)

## Windows backend: WASAPI, cables, tray (S6)
Everything here is **unproven**: it compiles for `x86_64-pc-windows-gnu` and its decisions are unit-tested on Linux (`win_rules`, `pcm`), but it has never opened a Windows device. `tests/wasapi_live.rs` and `docs/windows-testing.md` are for the first run on a Windows machine.
- **W1** [by design] One worker thread per stream (`win/stream.rs`) that joins COM (MTA), asks MMCSS for "Pro Audio", opens the endpoint, reports success or failure to `open_*` (so a failed open returns the port), then waits on the WASAPI event (20 ms timeout, which also polls the stop flag) and moves audio through `ring_io` (`CaptureState`/`PlaybackState`, the same code as Linux, so the output side runs the drift resampler, law 2). `TimerMaster` still clocks the mixer, as on Linux (P2): no device-clocked master yet.
- **W2** [by design] Open order: exclusive (only with `WasapiOptions.exclusive`, hardware devices only, tries `f32`, 32/24-bit, packed 24, 16-bit via `pcm.rs`, smallest 128-byte-aligned period; a refusal is an error, never a silent fallback to shared) → shared `IAudioClient3` at the driver's minimum period (`WasapiOptions.low_latency`, default on; only when the engine's mix format is already 48 kHz `f32` with the channel count wanted, otherwise skipped) → classic shared event-driven, 48 kHz `f32`, `AUTOCONVERTPCM` so Windows converts rate, type and channels (A2). `AudioStream::detail()` says which one a stream got and the period. Device latency is two periods (the buffer is kept full), so `IAudioClient3` is the lever; the classic default is 10 ms periods, i.e. about 20 ms.
- **W3** [by design] Device ids are Windows endpoint ids (`{0.0.0.00000000}.{guid}`), `"default"` is the console-role default. Device loopback (`DeviceLoopback{device_id}`) names an *output* device, like PipeWire's monitor. A loopback of a silent device delivers **no packets at all**; the loop keeps polling and the strip simply sees an empty FIFO (silence) until sound starts.
- **W4** [by design] Process loopback needs build ≥ 20348 (`RtlGetVersion`, not `GetVersionEx`, which lies without a manifest). Below it `capabilities().process_loopback` is false, `apps()` is empty and opening answers `NotSupported` naming the build; it does **not** quietly record the whole device (PLAN §2 row 13 said "fall back to device loopback"; the UI does that by offering device loopback when the capability is off). The pid given is climbed to the topmost ancestor running the *same executable* (browsers, Discord, Electron) and the tree is included (`IncludeTree`) or excluded (`ExcludeTree`, "everything but this", the way to avoid feedback). The `wasapi` crate maps `include_tree: false` to *exclude*, whatever its docs say. The router's own audio sessions are never listed. Windows only supports these two modes, so "this process only, no children" does not exist. Channel counts other than 2 are untested with process loopback.
- **W5** [by design] Virtual devices come from installed software (we cannot make a kernel device): VB-Audio cables are recognised by name (`CABLE Input (VB-Audio Virtual Cable)`, CABLE-A/B, Hi-Fi Cable) and paired by the bracketed text. Cable n is *both* `VirtualInput{n}` (we record its output end) and `VirtualMic{n}` (we play into its input end), but one cable is one pipe, so opening it one way refuses the other (`Busy`); a second cable gives both. VoiceMeeter's own devices are deliberately not cables (they pass audio only while VoiceMeeter runs). The "Virtual Audio Driver" speaker is offered as a loopback-only virtual input; that name comes from the project's README and is **unverified**. Any other device still works as an ordinary hardware input/output.
- **W6** [fixable] If the device disappears or Windows reports an error mid-stream, the worker thread ends and `detail()` reads `STOPPED while …: …`; the stream's counters freeze but the control plane still says `Running` (same gap as P10, TODO). No automatic reopen. A default-device change while a "default" stream is open is not followed.
- **W7** [by design] `platform-io` is `deny(unsafe_code)` (was `forbid`) so that `win::sys` can call MMCSS, `RtlGetVersion` and the process snapshot; every block has a SAFETY note. `router-tray` is the same for its message loop. No other crate changed its policy.
- **W8** [by design] `router-tray` (Windows only; the binary prints a notice elsewhere, so the workspace builds without GTK) starts `routerd` if no engine answers, and starts/ends `router-ui` from its menu or a left click. Ending is `Child::kill` (no graceful path until C5); it forgets, not kills, its children when it quits unless "Quit tray and engine" is used on an engine it started itself. `router-ui` exists since S7 and is what the menu starts. The icon is drawn in code.
- **W9** [fixable] `WasapiOptions` has no UI/CLI knob yet (`routerd` uses the defaults: `low_latency` on, exclusive off, 8 ms output target). Exposing exclusive mode and the output target is a small `routerd` flag plus a profile field.

## Desktop UI: router-ui (S7)
Only the headless `egui_kittest` tests and one Xvfb run (software GL, mock `routerd`, Simple and Expert Strips screenshots) have run. No real GPU, Wayland, Windows or touch screen has.
- **U1** [by design] egui/eframe are pinned to **0.32.3** (glow renderer, features `glow, default_fonts, accesskit, x11, wayland`). eframe 0.37 needs Rust 1.95; the workspace MSRV is 1.85 (no let-chains in the code). `accesskit` is on because `egui_kittest` finds widgets by their accessible label, and because egui-winit 0.32 does not compile without it when eframe is built with default features off. Raise both together when the MSRV moves.
- **U2** [by design] The UI is a thin view: `Link` (a worker thread; `Link::inline` in tests) runs a `Session` that connects through `app_core::ipc`, fetches snapshot, devices and apps on connect, retries every second while the daemon is away, and rate-limits what it asks. `Model` keeps the newest snapshot and meters (meters polled at 30 Hz, snapshots every 0.5 s, 0.1 s after a command). Views read an immutable `Ctx` and push actions into `Out`; `app.rs` sends them after drawing. No view touches the engine. A "daemon not running" banner with "Start daemon" (spawns `routerd` detached; no console window on Windows) shows while the link is down, and the UI reconnects by itself.
- **U3** [by design] Commands are applied optimistically (`model::apply_command`) so a fader follows the pointer at once. A generation counter drops any snapshot that was requested before the newest command, so a slow reply cannot snap a control back. A refused command shows its reason in the status line, and the next snapshot restores the truth.
- **U4** [by design] Repaint (CLAUDE.md law 5) is decided in one pure place, `governor::RepaintGovernor`: minimized → no repaint at all (Rich and Eco), unfocused or silent for more than 0.5 s → `silent_fps`, otherwise `active_fps` (Rich 60/15, Eco 30/5). `RouterApp::run_frame` is the only place that requests a timed repaint, and only for `Repaint::After`. Two requests are not timers and are each bounded by user input: the worker's wake after a user command (8 ms, so a fader drag shares frames) and one `request_repaint()` after a frame that issued commands. A minimized window gets no wake from the worker for meters. The Wayland case (no minimized/focus info) is treated as visible and focused.
- **U5** [by design] Bus letters follow the sink: **A** is a `HardwareOutput`, **B** is everything else (LAN, virtual). Console Strips shows the used strips and buses plus one spare each with a "+" (the snapshot always has 16 + 16). Collapsing a column makes it a 28 px pillar (mute, meter, vertical name); 125 px otherwise. A right-click on a routing button opens the send knob (gain, pre/post) inline, never a popup window. Below 600 px the UI is narrow: columns start as pillars, touch targets are 44 px, and an inspector takes the whole page.
- **U6** [by design] Simple mode owns one strip/bus pair labelled "Simple send" and one labelled "Simple receive" (found by label, else the first free pair), so it never disturbs what Expert mode set up. Send picks an input or an app and a machine (found by discovery, or typed); Receive picks a sender and an output, and a network delay preset (Fast/Medium/Slow). The preset is chosen by the person, not measured (TODO, N3).
- **U7** [by design] The Record button and the Patchbay layout are drawn **disabled**. Recording is S9 (C4) and the engine's recorder ring has no consumer; Patchbay is S9. The Expert layout falls back to the strips if a profile asks for Patchbay.
- **U8** [fixable] The strip inspector shows the LAN receive counters, buffer and drift, but not Wi-Fi RSSI or link speed (nothing in the snapshot carries them), and there is no probe view (`router-cli probe` has it).
- **U9** [by design] The real-window check found a layout bug that kittest cannot see: two `horizontal_wrapped` cards in Simple mode were drawn at a stray offset and clipped. They are stacked now. Layout problems are not visible to the headless tests, which look at widget rectangles by label; look at a real window (TODO).
